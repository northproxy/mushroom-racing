# INSTRUCTIONS.md

# Mushroom Racing — правила работы с AI-ассистентом

## Назначение документа

Этот файл определяет правила совместной работы над проектом **mushroom-racing**.

Он является рабочим контрактом между владельцем проекта и AI-ассистентом и должен помогать:

- сохранять проект понятным и аккуратным;
- не терять архитектурные решения;
- не засорять репозиторий временными файлами;
- понимать смысл каждого важного изменения;
- поддерживать профессиональный уровень кода и документации;
- создавать проект, который позже можно без стыда показать работодателю или открыть публично.

Проект сейчас частный.

Если в будущем будет принято решение сделать его публичным, документация может быть переведена на английский отдельной фазой.

---

# 1. Язык проекта

## Общение

Всё общение между владельцем проекта и AI-ассистентом ведётся **на русском языке**.

К этому относятся:

- обсуждение архитектуры;
- объяснения;
- планы;
- отчёты;
- анализ ошибок;
- аргументация решений;
- описание следующих шагов.

## Документация

Вся внутренняя документация проекта пишется **на русском языке**.

Например:

- `README.md`
- `INSTRUCTIONS.md`
- `ROADMAP.md`
- `DECISION_LOG.md`
- документация модели;
- документация источников;
- описание фаз;
- исследовательские заметки.

## Код

Сам код оформляется по общепринятым профессиональным стандартам на английском языке.

На английском пишутся:

- имена файлов;
- имена модулей;
- классы;
- функции;
- методы;
- переменные;
- константы;
- структуры данных;
- сообщения исключений;
- технические идентификаторы.

Пример:

```python
def calculate_rainfall_score():
    ...
```

а не:

```python
def rasschitat_ocenku_dozhdya():
    ...
```

## Комментарии внутри кода

Комментарии и docstrings пишутся **на русском языке**.

Причина: владелец проекта должен иметь возможность открыть любой файл и быстро понять, зачем существует код и какую задачу он решает.

Комментарии должны объяснять прежде всего **смысл и причину**, а не очевидное действие строки.

Хорошо:

```python
# Используем накопленные осадки за 28 дней, потому что один сильный ливень
# может создать ложное впечатление восстановления почвы после длительной засухи.
```

Плохо:

```python
# Считаем осадки за 28 дней.
```

Главный критерий хорошего комментария:

> Прочитав комментарий, владелец проекта должен суметь объяснить другому человеку, зачем существует эта часть логики.

# 2. Стандарт шапки скриптов

Каждый самостоятельный скрипт должен начинаться с понятной служебной шапки.

Базовый формат:

```python
"""
File: rainfall_import.py
Project: mushroom-racing

Purpose:
    Загружает исторические данные осадков из выбранного источника
    и преобразует их во внутренний формат проекта.

Created:
    2026-09-14

Last modified:
    2026-09-14

Status:
    prototype

Lifecycle:
    temporary — удалить после завершения MR03, когда импорт будет
    перенесён в постоянный модуль приложения.

Inputs:
    CSV/JSON ответа внешнего источника погоды.

Outputs:
    Нормализованные погодные записи.

Dependencies:
    Python standard library

Used by:
    scripts/weather_pipeline.py

Notes:
    Скрипт существует только для проверки выбранного источника данных.
"""
```

## Обязательные поля

- `File`
- `Project`
- `Purpose`
- `Created`
- `Last modified`
- `Status`
- `Lifecycle`
- `Inputs`
- `Outputs`
- `Dependencies`
- `Used by`
- `Notes`

## Допустимые значения Status

Примерные категории:

```text
prototype
temporary
active
stable
deprecated
```

## Lifecycle

Поле `Lifecycle` должно отвечать на вопрос:

> Нужно ли оставить этот файл после того, как соответствующая часть проекта заработает?

Примеры:

```text
permanent — часть приложения
```

```text
temporary — удалить после MR03
```

```text
prototype — заменить постоянной реализацией после подтверждения концепции
```

Цель — не допустить накопления забытых тестовых и временных файлов.

# 3. Временные файлы и эксперименты

В проекте создаётся локальная папка:

```text
tmp/
```

Она предназначена для:

- одноразовых тестов;
- скачанных пробных данных;
- временных конвертаций;
- экспериментов;
- промежуточных результатов;
- черновых скриптов;
- файлов для ручного анализа.

`tmp/` должна находиться в `.gitignore`.

Содержимое `tmp/`:

- не является частью финального приложения;
- не должно попадать в GitHub;
- может удаляться без влияния на рабочую версию проекта.

Если эксперимент становится полезной частью проекта, его логика переносится в подходящий постоянный модуль.

После переноса временная версия удаляется.

# 4. Имена файлов и версионность

Запрещаются имена:

```text
script_v2.py
script_new.py
script_final.py
script_final2.py
new_parser.py
old_parser.py
test_final.py
```

История версий хранится в Git.

Если новая реализация полностью заменяет старую и проверена, старая версия не сохраняется рядом «на всякий случай».

Рабочая версия должна иметь нормальное стабильное имя:

```text
weather_import.py
scoring.py
species_profile.py
```

# 5. Стиль разработки

Если изменение простое и очевидное, нет необходимости отдельно документировать каждую мелочь.

Если изменение влияет на:

- архитектуру;
- структуру данных;
- внешний источник;
- scoring model;
- способ хранения данных;
- пользовательский workflow;
- безопасность;
- приватность;
- значимую зависимость,

AI-ассистент сначала должен:

1. объяснить проблему;
2. объяснить цель изменения;
3. предложить варианты;
4. показать плюсы и минусы;
5. получить решение владельца проекта.

Только после этого меняется архитектура.

---

# 6. Размер изменений

Если задача понятная, допускается реализовывать **крупный логически завершённый блок сразу**.

Не нужно искусственно дробить очевидную работу на множество микрошагов.

При этом каждый крупный блок должен:

- иметь понятную цель;
- иметь способ проверки;
- не смешивать несвязанные изменения;
- завершаться рабочим состоянием проекта.

---

# 7. Обучающий режим

Код и архитектура должны оставаться профессиональными.

Нет необходимости объяснять каждую строку Python автоматически.

AI-ассистент:

- пишет профессиональный код;
- объясняет цель важных решений;
- по запросу подробно объясняет любую конструкцию;
- не упрощает архитектуру до плохих практик только потому, что проект учебный.

Проект одновременно является:

- учебным;
- практическим;
- портфельным.

---

# 8. Как показывать изменения кода

При изменении существующего файла AI-ассистент должен:

1. кратко показать, что изменилось;
2. показать diff или эквивалентное краткое сравнение;
3. предоставить **полный итоговый файл**, готовый к замене.

Владелец проекта не должен вручную собирать файл из отдельных фрагментов.

## JavaScript

Если создаётся JavaScript-файл, его содержимое предоставляется как текстовый файл.

Например:

```text
app.js.txt
```

Причина: владелец проекта не может скачивать исходные `.js` файлы напрямую.

---

# 9. Минимальные изменения работающего кода

Работающий код не переписывается без причины.

Если существующая реализация:

- понятна;
- тестируема;
- решает задачу;
- не создаёт архитектурной проблемы,

предпочтительно изменить только минимально необходимую часть.

Большой рефакторинг допускается, если он:

- реально уменьшает сложность;
- устраняет технический долг;
- необходим для следующего этапа;
- улучшает архитектуру;
- имеет понятную пользу.

Перед значимым рефакторингом AI-ассистент объясняет причину.

---

# 10. Тестирование

Бизнес-логика проекта должна сопровождаться тестами.

Обязательны тесты для:

- scoring logic;
- преобразования данных;
- валидации;
- расчётов;
- domain model;
- критической обработки внешних данных.

Одноразовые вспомогательные скрипты могут не иметь отдельных unit tests, если тестирование не имеет практического смысла.

## Базовый инструмент

На первом этапе используется:

```text
pytest
```

Не подключаем дополнительные инструменты качества без реальной необходимости.

Позже, если проект станет достаточно большим, можно отдельно решить вопрос о:

- formatter;
- linter;
- static type checker;
- pre-commit hooks.

Минимализм важнее количества инструментов.

---

# 11. Fail-fast

Проект должен придерживаться принципа:

> лучше понятная ошибка, чем тихо испорченные данные.

Предпочтительны:

- явная validation;
- понятные exceptions;
- проверка обязательных полей;
- остановка при невозможном состоянии.

Не допускается:

- молча игнорировать критическую ошибку;
- подставлять случайные default values;
- делать вид, что операция прошла успешно.

---

# 12. Type hints

Python-код должен использовать type hints везде, где это разумно.

Цель:

- облегчить чтение;
- сделать интерфейсы понятнее;
- уменьшить число ошибок;
- повысить профессиональный уровень проекта.

---

# 13. Именование

Используются стандартные Python-конвенции:

```text
files               snake_case.py
functions           snake_case
variables           snake_case
classes             PascalCase

```

# 14. Зависимости

Минимализм — базовый принцип.

Новая внешняя библиотека добавляется только тогда, когда она действительно нужна.

Перед добавлением зависимости AI-ассистент должен объяснить:

- какую проблему она решает;
- почему стандартной библиотеки недостаточно;
- насколько библиотека распространена и поддерживается;
- будет ли она частью финального приложения;
- можно ли избежать зависимости без ухудшения проекта.

---

# 15. Секреты и credentials

Секреты никогда не хранятся в Git.

К ним относятся:

- API keys;
- tokens;
- passwords;
- private endpoints;
- приватные credentials.

Рабочие секреты хранятся локально в:

```text
credentials.md
```

Этот файл:

- находится вне Git;
- обязательно добавляется в `.gitignore`;
- никогда не публикуется.

Если приложению нужны переменные среды, можно использовать локальный `.env`.

В репозитории допускается только:

```text
.env.example
```

без реальных секретов.

---

# 16. Приватные грибные места

Точные реальные координаты успешных грибных мест считаются приватными.

Принцип проекта:

> грибник грибнику враг.

Публичный репозиторий никогда не должен содержать:

- точные координаты личных находок;
- приватные hotspot-данные;
- пользовательскую историю реальных секретных мест.

Для демонстраций используются:

- искусственные данные;
- обезличенные данные;
- округлённые координаты;
- специально подготовленные demo datasets.

---

# 17. Большие данные

Большие GIS-файлы, погодные архивы и исходные массивы данных не должны автоматически попадать в Git.

Используется структура:

```text
data/
├── raw/
├── processed/
└── samples/
```

В Git обычно сохраняются только:

- маленькие fixtures;
- samples;
- схемы;
- инструкции воспроизведения данных.

Большие данные должны быть воспроизводимы через documented import process.

---

# 18. Источники данных

Источники данных являются отдельной важной стадией проекта.

Для каждого внешнего источника фиксируется:

- название;
- provider;
- URL;
- какие данные он предоставляет;
- geographic coverage;
- resolution;
- update frequency;
- access method;
- API/download mechanism;
- license;
- ограничения использования;
- стоимость;
- дата проверки;
- известные недостатки.

## Финансовое правило

Проект разрабатывается без бюджета.

Используются только:

- бесплатные источники;
- open data;
- free APIs;
- официальные бесплатные сервисы;
- локально вычисляемые данные.

Если источник требует оплаты, он не интегрируется без отдельного решения владельца проекта.

---

# 19. Проверка внешних источников

AI-ассистент может самостоятельно проводить web research для проекта.

Перед значимым исследованием источника он объясняет:

- какой источник хочет проверить;
- какую проблему источник должен решить;
- какие данные нужны;
- как источник потенциально будет использоваться в финальной версии приложения.

После проверки фиксируется:

- подходит ли источник;
- как его использовать;
- ограничения;
- лицензия;
- стабильность;
- альтернатива при необходимости.

---

# 20. Недостающая информация

Если для важного решения не хватает информации, AI-ассистент не должен молча угадывать.

Он должен:

1. обозначить, чего не хватает;
2. предложить разумные варианты;
3. объяснить смысл каждого варианта;
4. спросить решение владельца проекта.

Для несущественных технических мелочей допускается выбрать очевидный стандартный вариант.

# 22. Контроль неопределённости

AI-ассистент обязан явно сообщать:

- что проверено;
- что предполагается;
- где данных недостаточно;
- какие тесты действительно запускались;
- что ещё не реализовано.

Запрещается утверждать:

```text
"работает"
"проверено"
"готово"
```

если соответствующая проверка реально не выполнялась.

---

# 23. Удаление файлов

Перед удалением постоянного файла AI-ассистент должен объяснить:

- зачем файл существовал;
- почему он больше не нужен;
- куда перенесена его функциональность;
- есть ли риск потери данных или логики.

Временные файлы внутри `tmp/` могут удаляться свободнее.

---

# 24. TODO

`TODO` разрешён, но не должен использоваться как бесконечная записная книжка.

Хороший TODO связан с конкретной стадией:

```python
# TODO(MR03): заменить тестовый JSON на данные реального погодного источника.
```

Плохой TODO:

```python
# TODO: потом исправить.
```

После завершения стадии связанные с ней TODO должны быть:

- выполнены;
- перенесены в явно зафиксированную следующую фазу;
- либо удалены как неактуальные.

---

# 25. Структура проекта

Базовое разделение:

```text
src/
    постоянная логика приложения

tests/
    автоматические тесты

scripts/
    самостоятельные служебные инструменты

notebooks/
    исследовательский анализ

tmp/
    локальные временные эксперименты

data/raw/
    локальные исходные данные

data/processed/
    производные большие данные

data/samples/
    маленькие воспроизводимые примеры

docs/
    только действительно необходимая документация
```

Структура может меняться, если новая структура:

- яснее;
- логичнее;
- уменьшает сложность;
- лучше отражает архитектуру продукта.

Структура не является догмой.

---

# 26. Новые файлы

Документация не должна раздуваться.

Новый файл создаётся только если он:

- отделяет самостоятельную область знаний;
- отделяет самостоятельную архитектурную ответственность;
- делает проект проще;
- предотвращает превращение существующего файла в свалку;
- нужен для воспроизводимости проекта.

Нельзя создавать документ только потому, что «так выглядит профессиональнее».

---

# 27. Документация

Документация обновляется после крупных изменений и завершения фаз.

Не нужно фиксировать каждую мелочь.

Минимальный набор постоянных документов должен оставаться небольшим и полезным.

Основные категории:

- что строим;
- как устроено;
- откуда берутся данные;
- как работает scoring;
- что решили архитектурно;
- где проект находится сейчас.

---

# 28. CHANGELOG

`CHANGELOG.md` ведётся минимально.

Он фиксирует:

- законченные значимые стадии;
- релизы;
- крупные функциональные изменения.

Он не должен превращаться в журнал каждого commit.

---

# 29. Decision Log

`DECISION_LOG.md` содержит только действительно важные архитектурные решения.

Примеры:

- rule-based model вместо ML;
- выбор основной БД;
- переход на конкретную GIS-технологию;
- изменение фундаментальной модели хранения данных;
- изменение способа расчёта final score.

Мелкие изменения формул и локальные технические решения не требуют отдельного ADR.

# 30. Milestones проекта

Milestones должны иметь:

- технический номер;
- короткое юмористическое название;
- понятную цель.

Формат:

```text
MR01_юмористическое_название
```

При этом само название стадии может быть на русском.

## Предлагаемая система

```text
MR00_споры_посеяны
MR01_грибница_данных
MR02_карты_на_стол
MR03_танцы_с_дождём
MR04_грибной_радар
MR05_в_лес_не_наугад
MR06_грибник_грибнику_враг
MR07_проверка_на_местности
MR08_укрощение_мицелия
MR09_выход_из_леса
```

### MR00_споры_посеяны
Repository baseline.

### MR01_грибница_данных
Domain model и базовые структуры данных.

### MR02_карты_на_стол
Исследование и фиксация бесплатных источников GIS/forest/soil/geology/legal data.

### MR03_танцы_с_дождём
Weather pipeline, осадки, температура, drought context.

### MR04_грибной_радар
Первая рабочая scoring model.

### MR05_в_лес_не_наугад
Карта и ранжирование участков.

### MR06_грибник_грибнику_враг
Приватность пользовательских находок и хранение observations.

### MR07_проверка_на_местности
Полевое тестирование и сбор положительных/отрицательных наблюдений.

### MR08_укрощение_мицелия
Калибровка модели по фактическим данным.

### MR09_выход_из_леса
Подготовка GitHub showcase / portfolio release.

Названия можно менять по мере развития проекта.

# 31. Definition of Done

Каждая фаза должна иметь измеримые критерии завершения.

Для стадии обязательно фиксируются:

- цель;
- deliverables;
- способ проверки;
- команды тестирования;
- ограничения;
- что считается завершением.

Нельзя считать фазу завершённой только потому, что «код написан».

# 32. Git workflow

На текущем этапе используется одна основная ветка:

```text
main
```

Сложные branching strategies пока не нужны.

Git должен отражать логические стадии проекта.

После завершения каждой значимой фазы AI-ассистент предлагает commit message.

Пример:

```text
feat: complete MR01 domain model
```

или:

```text
data: complete MR02 Austrian source registry
```

---

# 33. Portfolio-first engineering

Одна из главных целей проекта — профессиональное развитие владельца.

Проект должен демонстрировать потенциальному работодателю:

- аналитическое мышление;
- способность исследовать неизвестную предметную область;
- умение превращать знания в формальную модель;
- работу с GIS и внешними данными;
- проектирование структуры данных;
- тестирование;
- документирование;
- критическое использование AI;
- способность проверять результат AI, а не просто копировать его;
- способность доводить идею до работающего продукта.

AI-ассистент является инструментом разработки, но архитектурные решения должны оставаться:

- понятными владельцу;
- объяснимыми;
- контролируемыми;
- воспроизводимыми.

Цель — не создать впечатление:

> «AI написал приложение».

Цель — показать:

> «владелец проекта умеет использовать AI как инженерный инструмент для исследования, проектирования, разработки и проверки продукта».

# 34. Публичность

Хотя проект сейчас частный, код пишется так, будто в будущем репозиторий станет публичным.

Это означает:

- аккуратные имена;
- отсутствие секретов;
- отсутствие мусорных файлов;
- воспроизводимую структуру;
- понятные commits;
- тестируемость;
- честное описание ограничений;
- отсутствие ложных заявлений о возможностях модели.

---

# 35. Главный принцип проекта

Приоритеты:

1. качество мышления;
2. понятность архитектуры;
3. контролируемая работа с AI;
4. корректность;
5. воспроизводимость;
6. профессиональная документация;
7. работающий продукт;
8. скорость.

Скорость важна, но не должна разрушать остальные пункты.

# 36. Главное правило взаимодействия

Если существует выбор между:

> «быстро сделать магию»

и

> «сделать систему, которую можно понять, проверить и объяснить»,

выбирается второй вариант.

`mushroom-racing` должен быть не только приложением для поиска грибов, но и доказательством инженерного мышления владельца проекта.
